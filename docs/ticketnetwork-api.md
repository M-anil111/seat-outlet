# TicketNetwork API: access, orders, limits, opportunities, copy policy

Prepared 2026-10-04 for Seat Outlet (PHP ticket-comparison site; it does not sell tickets, orders are fulfilled through TicketNetwork).

## Read this first: what could and could not be verified

TicketNetwork does not publish its Catalog API reference on the open web. The developer portal at https://console.tn-apis.com is a login-gated WSO2 portal: the public store page (https://console.tn-apis.com/store) renders "No APIs Available" without a session, and the login page (https://console.tn-apis.com/devportal/services/configs) offers sign-in and "Create Account" only. The host `developer.ticketnetwork.com` does not resolve (DNS failure when fetched on 2026-10-04). So:

- **Verified (public)** means the statement is on an official TicketNetwork page that was fetched, URL given.
- **Verified (repo)** means seen in this repository's code or in a documented live test recorded in the repo (file given).
- **Inference** means reasoned from the above, not proven.
- **Needs confirmation** means only TicketNetwork can answer; it is repeated in "Questions to send TicketNetwork".

No endpoint, limit, price or commission rate below is invented. Where the official reference was not reachable, the doc says so instead of guessing. Anyone with a portal login should compare this file with the API reference inside the portal and promote Inference items to Verified.

## 1. Login, registration and API credentials

There are two separate TicketNetwork programs. Mixing them up is the most likely source of confusion.

| Program | What you get | Fits Seat Outlet today? |
|---|---|---|
| Affiliate program (links, widgets, commission) | A publisher ID (PID) on an affiliate network, tracked links, Event List, Search and Calendar widgets | No. It is link and widget based, not the API this site uses |
| API / integration (Catalog API, Mercury Web Services, Seatics maps, hosted checkout) | OAuth app credentials, a website config id, sandbox then live | Yes. This is what the repo calls |

### 1.1 Affiliate program (Verified, public)

- Sign-up happens on a third-party affiliate network, not on TicketNetwork. Preferred networks listed: Impact, Commission Junction, Rakuten (the page text also says "four preferred networks" and names ShareASale elsewhere, but only three sign-up buttons are shown). Source: https://www.ticketnetwork.com/en/affiliate-signup
- Tools (Event List Plugin, Search Widget, Calendar Widget) track by your PID across those networks. Source: https://www.ticketnetwork.com/en/affiliate-tools
- Commission rates are not published on these pages. Needs confirmation.

### 1.2 API credentials (what the repo shows, plus what is public)

Verified (repo):
- Token: `POST https://key-manager.tn-apis.com/oauth2/token`, HTTP Basic auth with consumer key and secret, body `grant_type=client_credentials`. Source: `.github/workflows/tn-check.yml`, `functions.php` (token code near the top).
- The token response includes `access_token`, `token_type`, `expires_in` (about one hour; `functions.php` caches it for "a full hour"). The scope is whatever the app is subscribed to.
- Catalog calls send `Authorization: Bearer <token>` and the header `X-Listing-Context: website-config-id=<id>` (`functions.php` tnBuildHandle; `tn-check.yml`).
- Two environments: sandbox `https://sandbox.tn-apis.com` (website config 12498) and live `https://www.tn-apis.com` (website config 27773). Ids from one environment do not work with the other config (`inc/constants.php`, CONTRIBUTING.md "Purchase flow").
- Credentials are env vars `CONSUMER_KEY` and `CONSUMER_SECRET` (`.env.example`).
- Token rotation: TicketNetwork invalidates an app's previous token a few seconds after issuing a new one (recorded as "verified" in CONTRIBUTING.md). Every process (web and cron) must share one token store.
- `docs/launch-checklist.md` records that the original key pair was committed to a public repo and must be rotated, and that the old pair "may be sandbox-only".

Verified (public):
- The developer portal is a WSO2 API Manager portal at https://console.tn-apis.com with account creation and an "apim:subscribe" / "apim:app_manage" scope set in its login redirect, which matches the standard WSO2 flow: create an account, create an application (this yields consumer key and secret), subscribe the application to APIs. Source: https://console.tn-apis.com/devportal/services/configs

Inference:
- The consumer key and secret are generated by creating an "Application" in that portal, and the Catalog API must be subscribed to that application. The 403 "API Subscription validation failed" that Mercury returns (checkout.php, seatics doc) is the standard WSO2 message for an application that is not subscribed to that API, so it means "subscription missing", not "bad credentials".
- The website config id is issued by TicketNetwork staff per site (it carries checkout URL, post-purchase redirect and branding; `docs/seatics-checkout-thankyou-implementation.md`). It is not self-service.

## 2. Orders: placement, tracking, cancellations, delivery, commissions

### 2.1 What TicketNetwork documents publicly

Verified (public), Mercury Web Services, https://mercurywebservices.com/ and https://corporate.ticketnetwork.com/products-services/mercury-retail-integrations/:
- Orders are real-time: tickets are secured and locked while the client charges its customer's card and reviews the order for fraud; orders are "automatically accepted and confirmed, all within a matter of seconds".
- Inventory is supplied at broker wholesale price; the client controls markup, service fees and shipping. This is a merchant-of-record model: the client takes payment and delivers tickets.
- Guarantee: Mercury transactions are guaranteed at the higher of 200% or the cost of replacement tickets; fill rate stated as 99.98% (TicketNetwork's own claim).
- Client portal (WebAdmin): review and manage transactions, invoices and bills, create airbills, submit support tickets.
- Customer service for the buyer is provided by the client, with TicketNetwork support behind it for order problems.
- Free access to the Seatics Maps API.

Not published (Needs confirmation, all of it): the order create, status, cancel and refund endpoints and payloads; hold duration; delivery status or tracking callbacks; webhook events; settlement and reporting feeds. Do not build against any guessed path.

### 2.2 What this repo does today (Verified, repo)

- Seat selection: Seatics MapWidget3 on `event.php`, keyed by `WEBSITE_CONFIG_ID`.
- Payment and order creation happen entirely on TicketNetwork's hosted white-label checkout at `TN_CHECKOUT_URL` (`https://checkout.seatoutlet.com` by default, requires a DNS CNAME arranged with TicketNetwork). That checkout locks the ticket group, takes payment, runs fraud screening and handles delivery (`checkout.php` header comment).
- `checkout.php` is an optional branded review page that passes `tgid`, `qty`, `prc` through. It is currently not linked from anywhere (`docs/launch-checklist.md` item F1).
- `order-confirmation.php` is the post-purchase landing page. It reads `oid`, `total`, `eid` from the URL, shows "Purchase complete" only if the visitor clicked Buy within 24 hours (cookie `so_checkout`), and fires a GA4 `purchase` event once per order number. The file states it is hardening, not proof.
- No order table, no order status, no webhook receiver, no commission or revenue data are stored. `grep` finds no use of `/mercury` other than the explanatory comment in `checkout.php`.
- Mercury calls return 403 "API Subscription validation failed" on the current subscription (recorded as verified in `checkout.php`, `inc/constants.php`, CONTRIBUTING.md).

### 2.3 The gap

| Need | Today | Gap |
|---|---|---|
| Know an order happened | Browser lands on `/order-confirmation` with URL params | Not server-confirmed; blocked ad-blockers, closed tabs and forged URLs distort revenue. A server-side order postback or webhook is not available or not known |
| Order status, cancellations, refunds | None on our side; buyer deals with TicketNetwork | No visibility; support requests from buyers cannot be answered from our data |
| Commission and reporting | Unknown | No documented source. Needs confirmation of the commercial model (see below) |
| Delivery tracking | Buyer sees what TicketNetwork shows | None |
| Redirect parameters | Assumed `oid` | Parameter names after checkout are unconfirmed (`docs/seatics-checkout-thankyou-implementation.md`) |
| Checkout host | `checkout.seatoutlet.com` has no DNS record per the seatics doc | Must be arranged with TicketNetwork before launch |

Commercial model: Inference only. Because the checkout is TicketNetwork's hosted one and Seat Outlet never touches card data or inventory, Seat Outlet is probably paid a referral or revenue share on completed orders, not a markup. The repo contains no contract term, rate or reporting source. Needs confirmation: how commission is calculated (percentage of order, of margin, or fixed), how it is reported (portal, report, feed), payment schedule, and treatment of cancellations and refunds (clawback).

### 2.4 Two ways forward

1. **Stay on hosted checkout (recommended now).** Ask TicketNetwork for an order postback or webhook, signed or with a shared secret, delivering order id, event id, total, quantity, status. Store it in our database; reconcile against GA4. Effort M once TicketNetwork enables it.
2. **Own the checkout via Mercury.** Requires approval, subscription enablement, PCI scope, fraud handling, customer service, refund handling, and Seat Outlet becoming the merchant of record. That contradicts the current positioning (Seat Outlet compares listings and does not sell tickets). Effort L, plus legal and compliance work. Do not pursue without a business decision.

## 3. Rate limits, throttling, caching and terms of use

### 3.1 What the site experiences (Verified, repo)

- `/catalog/v2/events` answers HTTP 429 or a JSON error with a code matching `9008xx` ("Message throttled out", quota exceeded). `tnParseResult()` in `functions.php` treats both as throttling.
- Sentry shows 9 throttle events in 2 hours on 2026-10-04 (`docs/reliability.md`). Cold pages and crawler traffic trigger it. The `docs/reliability.md` text says "Ask TicketNetwork support for the per-second and daily limits on our key".
- The `9008xx` code pattern and the phrase "Message throttled out" are WSO2 API Manager throttling responses. Verified on 13 Oct 2026 (Sentry, the 429 body): the code is **900804**, which in WSO2 is the *subscription-level* throttle (900800 API level, 900803 application level, 900804 subscription level). So the limit is the throttling tier TicketNetwork attached to our application's subscription to the Catalog API, and only they can change it. Measured the same day: a steady 1 call a second is almost never refused (2 in ten minutes), 2 a second with bursts of 4 is refused 37 times in ten minutes with the same number of calls that got through, so the tier is about one request a second with little or no burst allowance.
  **Confirmed by TicketNetwork on 14 Oct 2026: the limit is 50 requests a minute per API** (their reply did not say whether it is per application, subscription, IP or website config, whether the window is rolling or fixed, or whether a higher tier exists). That matches the measurement: 460 calls in ten minutes is 46 a minute. They also confirmed the live key is production and active with the Catalog API subscription, that Retry-After or quota headers on 429s would be a feature request, and that they have no written cache-age rule to give. The bulk endpoint needs an additional role and new keys (section 8).

### 3.2 What TicketNetwork documents publicly

Verified: nothing. No public page states a request-per-second, per-minute or daily limit, a quota, a `Retry-After` convention, or caching and data-retention terms for Catalog API data. The portal's API reference may contain them. Needs confirmation.

### 3.3 What the repo already does to stay within limits (Verified, repo)

File cache per endpoint (reference data 6 h, event lists 10 min, search 5 min, suggest 1 h), stale-while-revalidate, a circuit breaker per family of calls (events and reference data; 20 s for ordinary errors, `TN_BREAKER_SECONDS`; 60 s or the server's `Retry-After` for a throttle, `TN_BREAKER_THROTTLE_SECONDS`), a shared call budget (`TN_CALLS_PER_SECOND`, default 0.75, 45 a minute), stale-on-error limits (event lists and details 2 h, stored event copies 24 h, reference data 14 days), page snapshots, parallel prefetch limited, crons that stop when throttled. The warmer visits event details in batches of up to 40 per 15-minute run with a stored cursor.

The code constants are the source of truth. `docs/reliability.md` ("Removed events and stale answers") and CONTRIBUTING.md list the same windows.

### 3.4 Terms-of-use risk on cached data

Inference and Needs confirmation. When the live call fails, the site serves stored event data for at most 2 hours (event lists and details), 24 hours (stored event copies and the database snapshot), or 14 days (reference data only: performers, venues, categories). Full rendered page snapshots (`soSnapshotServe()`) can also be served for up to 14 days and may contain event prices that have since changed. Prices and availability change in minutes. If TicketNetwork's terms limit caching or display of catalog or price data, or require showing live prices, these copies and 14-day page snapshots may breach them. Until the rule is answered, copy-served event pages should show "prices as of" the time the copy was seen (done for event pages), and snapshot-served pages should identify the price date or omit stale prices. Also confirm whether structured data (schema.org Offer/price) from cached prices is allowed.

### 3.5 What to ask TicketNetwork to raise

- The numeric limits on our key (per second, per minute, per day) for sandbox and live, separately, and which header or error body reports remaining quota.
- A higher tier for the live application, with the traffic reason: SEO crawl (hundreds of thousands of long-tail URLs), cron warmers, and organic traffic growth.
- Whether the throttle is per application, per IP or per website config, and whether adding our server IPs to an allow list is possible.
- Whether bulk or feed access (section 4) can replace per-page calls.

## 5. Copy policy

Purpose: stay accurate about the business model and avoid claiming things only TicketNetwork can promise. Several existing pages already say "our guarantee" or "Buyer Protection Guarantee" (`checkout.php`, `ticket-buyer-protection.php`); `docs/launch-checklist.md` asks counsel and TicketNetwork to confirm these. Review them against this policy.

### 5.1 Approved wording

- "Seat Outlet is a ticket comparison site. We compare listings from sellers on the TicketNetwork marketplace; we do not sell tickets."
- "Orders are placed and fulfilled through TicketNetwork."
- "You pay on TicketNetwork's secure checkout. TicketNetwork ships or delivers your tickets."
- "Orders are covered by TicketNetwork's guarantee" followed by a link to TicketNetwork's own terms. Quote only what TicketNetwork publishes. Public text on https://www.ticketnetwork.com/en/affiliate-tools says "All Tickets are backed by a 100% Guarantee. Your tickets will arrive before the event. Your tickets will be valid for entry."
- "Prices and availability can change. The final total, including fees, is shown before you pay." (matches the current `checkout.php` text; confirm fee wording with TicketNetwork and counsel.)
- "Seat Outlet may earn a commission when you buy through links on this site." Use only after the commercial model is confirmed and subject to counsel review for disclosure rules.
- "Seat Outlet is not affiliated with, endorsed by or sponsored by the artists, teams, venues or event organizers named on this site."

### 5.2 Phrases to avoid

- "Buy from Seat Outlet", "we sell tickets", "our tickets", "our inventory", "ships from us", "we guarantee your tickets" (we are not the seller or guarantor).
- "Official tickets", "official site", "face value", "primary seller", "box office" (listings are resale marketplace listings).
- "Cheapest guaranteed", "lowest price", "best price" without a dated comparison basis.
- "No hidden fees" or "all-in price" until TicketNetwork confirms that displayed prices include fees (open question in `docs/launch-checklist.md`).
- "Verified seats", "tickets together", "instant delivery" unless TicketNetwork confirms the specific claim.
- "Refund guaranteed" or any refund promise stated in Seat Outlet's own voice; refer to TicketNetwork's policy.
- Promo codes TAKE5 and TAKE10 until TicketNetwork confirms them (launch checklist). Owner-confirmed 2026-10-24; SO_PROMOS_OFF=1 hides them.
- "Partner of" or using TicketNetwork logos or marks beyond what TicketNetwork's brand terms allow. Needs confirmation of brand usage rules.

### 5.3 Where to apply it

Footer or site-wide disclosure, checkout review page, order confirmation page, `terms-and-conditions.php` (add TicketNetwork as fulfillment partner per launch checklist), buyer-protection and guarantee pages, FAQ answers, `ticket-partner-program.php` (currently says "online resale ticket marketplace"), `about-seat-outlet.php`, schema.org organization description.

## 6. Verified against the sandbox (2026-10-12)

Source: the TicketNetwork "API Authorization" guide (V1.0) and the "API Client DevPortal Guide" (v4.0, 12/26/2025), plus live sandbox calls with the TestApplication. Credentials were used for these calls only and are not stored anywhere in the repo.

- **Token:** `POST https://key-manager.tn-apis.com/oauth2/token`, HTTP Basic (consumer key and secret), `grant_type=client_credentials`. Response: `access_token`, `token_type` Bearer, `expires_in` 3600. Refresh a couple of minutes before expiry (the code refreshes 120 s early).
- **Device scopes:** `scope=default device_<name>` gives one token per device. A new token revokes the previous token with the same scopes, so web and cron use separate device tokens (`device_web`, `device_cli`; set `TN_DEVICE_ID` per host). Two device tokens were checked together: both stayed valid.
- **Expired or revoked token:** HTTP 401 with fault code 900901. The guide says to generate a new token and retry once. Single requests refresh and retry once for JSON 401 responses; bulk prefetches may make an additional request before that retry.
- **Identity header:** `X-Listing-Context: website-config-id=12498` returns 200 with results on the sandbox. `X-Identity-Context` returns 400 with the same config id (tested 2026-10-12). The code keeps `X-Listing-Context`. Check with TicketNetwork (IntegrationSupport@TicketNetwork.com) if their documentation names `X-Identity-Context`.
- **Throttling:** the DevPortal says the subscription tier controls throttling. The sandbox subscription is the Trial tier. The sandbox responses carried no rate-limit headers (no Retry-After, no quota headers). The production tier and limits must come from TicketNetwork WebSupport.
- **List answers:** `GET /catalog/v2/events/` returns `{count, page, results: [...], _links, facets, spellcheck}`. Each row has `id`, `text.name`, `venue.text.name`, `city.text.name`, `date.date`, `stateProvince`, `country.alphaCode`, `defaultCategory`, `_metadata`. Before this check, `tnListRows()` read only an `events` key, so listing copies were never saved. Fixed.
- **Detail answers:** `GET /catalog/v2/events/{id}` has the same fields plus `_metadata.hasTickets`. `pricingInfo` was absent for an event without tickets; the event page already handles that.
- **Other paths checked (200):** `/catalog/v2/events/search?q=...`, `/catalog/v2/performers`, `/catalog/v2/performers/{id}`, `/catalog/v2/venues/`, `/catalog/v2/venues/{id}`, `/catalog/v2/cities`, `/catalog/v2/cities/{id}`, `/catalog/v2/suggest?q=...`, `/catalog/v2/categories/`, `/catalog/v2/stateProvinces/{id}`, `/catalog/v2/countries/{alpha}`, `/catalog/v2/postalCodes/`. A bad event id (999999999999) returns 400, which the code treats as "not found".
- **Credentials:** the DevPortal guide contains a plain-text login for the store account, and the consumer secret was shared in chat. Both should be rotated. Production keys come from TicketNetwork WebSupport, not the DevPortal.

## 8. Bulk endpoint form, DevPortal guide and API Authorization guide reviewed (2026-10-14)

Sources: "API Bulk Endpoint User Request Document" (one page), "API Client DevPortal Guide" v4.0 dated 12/26/2025 (issued to the DevPortal account that owns our sandbox TestApplication; it contains a plain-text DevPortal login that must not be copied into the repo, chat or tickets), and "API Authorization" V1.0 (2024).

**Bulk endpoint (Verified from the form; the endpoint itself is documented in the Swagger and in section 9).** TicketNetwork grants it "on an as needed basis" for marketing needs, reviews the answers, and may revoke access at any time. The form asks five things: Catalog API access in sandbox or production; architecture and planned use of the data; how often it will be called; acknowledgement of reasonable use with a recommendation to pull one request at a time; acknowledgement that it needs an additional role in the DevPortal and that an existing integration must implement new keys. The form goes to the account manager, not into the portal. The path, fields and update filters are in the Swagger file (section 9); its own rate limit is still not stated. Do not build an importer until the role is granted.

**Production keys.** The DevPortal guide says production tokens cannot be created in the DevPortal; TicketNetwork WebSupport provides all production keys. So the new keys for the bulk role come from WebSupport for production and from the DevPortal for sandbox. The consumer key and secret differ between sandbox and production for the same application (Authorization guide).

**Sandbox subscriptions.** The TestApplication is subscribed to CatalogAPI V2 and TNWebServiceInventory on the Trial tier ("the tier controls the throttling"). The guide says requests against WCID 12498 are allowed "for ONLY CatalogAPI" and WCID 22845 is allowed as well, which reads as the website config for the inventory (SOAP) API. Needs confirmation before any SOAP probe: use 22845, not 12498, for TNWebServiceInventory in sandbox. When adding a new application the DevPortal asks you to choose a request quota.

**Official reference.** The API's Overview and Try Out pages offer the Swagger UI definition and a Postman collection for download, and the Documents tab holds the supplemental documents. Download the Catalog API Swagger file and give it to the developer: it replaces the "reference not reachable" caveat at the top of this file and lets the field list, filters and limits be verified instead of inferred.

**Token handling (Verified against the Authorization guide, no code change needed).** Form POST to `/oauth2/token` with Basic auth and `grant_type=client_credentials`; `expires_in` 3600; refresh a couple of minutes early (the code refreshes 120 s early); a new token with the same scopes revokes the old one; one token per device with a `device_<id>` scope (the code uses `device_web` and `device_cli`); 401 with fault code 900901 means generate a new token and retry (the code retries once). `/oauth2/revoke` exists and is unused. The DevPortal's "Get Test Key" button overrides the access token and must not be used.

**Open points.**
- The Authorization guide says Maps API v3 client-side calls authenticate with `consumerKey` in the query string and still need JWT tokens generated periodically, or the map requests are denied. The repo does not use `consumerKey` (the Seatics widget is keyed by the website config), so this probably does not apply. Ask TicketNetwork to confirm that the event-page map does not depend on a recent token.
- The guide says anyone holding the secret can make calls and that their calls "count against your API throttle limits". An earlier key pair was committed to a public repo and a secret was pasted in chat. No evidence that this affects the 50-a-minute limit (our own logs account for about 46 calls a minute), but ask TicketNetwork to review activity on the application, as the guide itself advises, and rotate the credentials.

## 9. Catalog API Swagger, Basics guide, OData guide, DevPortal view and WSDL reviewed (2026-10-14)

Sources: the Catalog API v2 Swagger (three identical copies: `document.yaml`, `swagger.json`, `swagger_2.json`, host `www.tn-apis.com`, base path `/catalog/v2`), "Catalog API Starter Documentation" (Basics), "Catalog API OData Filtering Reference", the Postman collection, the TNWebServicesInventoryAPI v4 WSDL, and a read-only walk through the DevPortal made in the site owner's browser. This replaces the "reference not reachable" caveat at the top of this file for everything below.

**Throttling tiers (Verified in the DevPortal).** The Catalog API Overview lists these tiers: Trial (60 a minute), 50permin, 100PerMinute, 600permin and Premium (3000 a minute). TNWebServicesInventoryAPI adds a 1000-a-minute tier. The sandbox TestApplication carries the application policy 50PerMin. TicketNetwork's reply said production is 50 a minute, which is the 50permin tier. At 3 to 5 calls a second we need 180 to 300 a minute, so 100PerMinute (1.7 a second) is not enough and **600permin (10 a second) is the tier to ask for**. No per-second or per-day limit, Retry-After text, cache rule or data-retention rule appears in the Swagger, the Basics guide or the Documents tab. Both sandbox subscriptions show the status PROD_ONLY_BLOCKED; in WSO2 that normally means the subscription is blocked for production use through the DevPortal and open in sandbox, which fits "production keys come from WebSupport" (Inference, confirm with TicketNetwork). No scopes appear under OAuth 2.0 (only the implicit flow); Mercury and any "Bulk" API are not listed.

**`/events/bulk` (Verified, Basics guide and Swagger).**
- Up to 10,000 events a request (Swagger default 10000 per page); about 20 seconds for 10,000 and 10 seconds for 5,000 on average, sometimes slower, so set long timeouts.
- Page with `sort=createdAt,id` so new events land at the end; one request at a time, never parallel.
- `fields=*` returns everything; `fields=id,text/name` returns a subset. Default fields include id, date, takedownAt, isTest, name, geoLocation, ticket counts and prices; others, such as `uriComponent`, `uriComponentHistory`, `scheduleStatus`, `text/notes`, `version`, `createdAt` and `updatedAt`, are opt-in.
- Full refresh about once a day; afterwards pull only changes: `filter=metadataInclusiveUpdatedAt ge <time>` when the cache holds `_metadata` (hasTickets, ticketCount) and `filter=updatedAt ge <time>` when it does not. TicketNetwork's own example runs it hourly.
- Filters worth using: `takedownAt`, `isTest`, `_metadata/hasTickets`, `date/date`, `pricingInfo/lowPrice/value`, `defaultCategory/path`, `venue/id`, `performerFilter`, `categoryFilter`, `geoFilter`; `includeExcludedEvents` shows de-listed events.
- Only events have a bulk endpoint. Performers, venues, cities and categories are paged through their normal endpoints (`includeTotalCount`, `page`, `perPage`).

**Importer (built, off by default).** `cron/tn-bulk-import.php` (helpers in `inc/tn-bulk.php`, tables `tn_bulk_events` and `tn_bulk_state` from migration 0050) implements this plan and does nothing unless `TN_BULK_ENABLED=1`. It is not enabled because the bulk role has not been granted, and the field shapes were checked against the Swagger model, not a live answer. It asks for `sort=createdAt,id`, a field list of 31 names, `perPage` 5000 (`TN_BULK_PER_PAGE`), one request at a time, each call taking a token from the shared budget. A run ends on the first empty page, not a short one, because the Swagger pager text says a page holds at most 200 while the Basics guide says 10,000. A throttle opens the events breaker, stops the run and saves progress; the next run resumes. Old rows are deleted only after a full run that reached the end and saw at least half the previous count. Nothing on the site reads the table yet. First live use: save one real response and run `php cron/tn-bulk-import.php --file=page.json --dry-run` to check the mapping, then enable it.

**Where the bulk data would help.** A daily full import plus an hourly changes pull would give a local copy of every event with its venue, city, category, performers, `hasTickets`, ticket count and low, average and high price. Listing, search, sitemap and "ended event" pages could then read the local copy instead of making per-page live calls, which is the call volume that hits the 50-a-minute limit. Run it from a CLI cron (not a web request), one request at a time, perPage 5000 to 10000, timeouts of 60 seconds or more, and record the last successful `updatedAt` so a failed run resumes. Keep live calls for the event detail page and the Seatics map. TicketNetwork describes this cache pattern itself, but it has still given no written maximum age for prices, so keep "prices as of" on any page that shows a stored price.

**Other findings.**
- `/events/search` supports `expandSearch`, `timeOfDayFilter`, `includeFacets`, `facetFields` and `facetLimit`; there are suggest endpoints for events, performers, venues and cities, plus `/categoryhierarchies`. Events carry `uriComponent` and `uriComponentHistory` (a slug and its past slugs), `eventPriority`, `scheduleStatus` and `takedownAt`, none of which the site reads today. Whether `uriComponent` could replace or feed our own slug registry is a separate question.
- The OData guide confirms the operators the site uses (`eq`, `ne`, `gt`, `ge`, `lt`, `le`, `and`, `or`, `not`, `in`, grouping, `contains`, `startswith`, `endswith`) and adds `ancestorsOf` and `descendantsOf` for categories. String literals go in single quotes with a quote doubled to escape it. Sorting by distance needs a `geoFilter`.
- The TNWebServicesInventoryAPI v4 WSDL lists 25 operations: the 24 in section 7 plus `GetMapsData`. None creates or reads an order.
- The Postman collection and the Swagger carry the same endpoint set, so neither adds fields beyond the above.
